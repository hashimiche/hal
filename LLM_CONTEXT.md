# HAL CLI - Supplemental Repo Context

Use this file as a concise, repo-local supplement to [.github/copilot-instructions.md](.github/copilot-instructions.md).

Canonical behavior rules, user interaction rules, and build/test commands belong in [.github/copilot-instructions.md](.github/copilot-instructions.md). This file should stay focused on repo-specific architecture patterns and implementation lessons that are easy to forget during code generation.

## Command Architecture

### 1. Two-Tier CLI Structure
Separate infrastructure lifecycle from feature lifecycle to avoid flag collisions.

- Tier 1 core products use explicit verb subcommands.
    - Examples: `hal vault create`, `hal boundary delete`, `hal terraform status`
- Tier 2 feature/integration flows use noun subcommands with lifecycle actions.
    - Examples: `hal vault oidc enable`, `hal boundary mariadb disable`, `hal boundary ssh update`

### 2. Smart Status Default
If a command is run without lifecycle action, default to a read-only status view instead of Cobra help.

- Inspect Docker/Podman or the product API first.
- Summarize state as up, down, or degraded.
- Always end with a copy-pasteable `Next Step` command.

### 3. Destructive Cleanup Pattern
For product-level delete flows, prefer deleting the known local ecosystem directly instead of relying on the product API.

- Keep an explicit list of containers and volumes tied to the product.
- Use fast local teardown even if the service itself is unhealthy.

## Implementation Patterns

### 4. Output Hygiene
- Use `exec.Command(...).Output()` for read-only container checks when stderr noise from the engine would pollute UI output.
- Keep user-facing output short, state-oriented, and action-oriented.
- **Standardized installer-style output (`internal/ui`)**: long-running create/enable flows should use the shared `ui` package instead of ad-hoc `fmt.Println` + emoji.
  - `ui.Title(...)` prints a persistent header. `ui.Start()` begins a progress flow; each `ui.Step(...)` overwrites the previous line with an animated Braille spinner (single updating line, like a software installer). `ui.Stop()`/`ui.Fail(...)` end the flow.
  - Non-TTY (piped/MCP) degrades automatically to one plain `→ step` line each; the global `--verbose` flag forces the same per-step lines on a TTY.
  - The "command is done" block uses `ui.Success`/`ui.Section`/`ui.Field`/`ui.Item`/`ui.Hint` for a consistent summary across products.
  - **Credential placement rule**: command output shows credentials with immediate demo value (e.g. Vault OIDC `alice`/`bob`); operator/admin credentials (e.g. Authentik `akadmin`) live in `hal creds status` and the product's `status`/`-h`, not in the enable summary.
  - **Pilot**: `hal vault oidc enable/status` is the reference implementation; the Authentik integration (`internal/integrations/authentik.go`) routes its start/wait substeps through `ui.Step`. Roll the same pattern out to other products after review.

### 5. Local Infrastructure Gotchas
- Docker volumes cannot be removed while attached containers are running; feature disable flows often need in-container cleanup instead of volume deletion.
- On rootless engines, privileged internal ports may need high host-port mappings while keeping the original internal port for container-to-container traffic.
- Multi-line payloads passed into Linux containers from Go should strip `\r` first with `strings.ReplaceAll(text, "\r", "")`.
- Some older Linux binaries bundled in images can fail on Apple Silicon under Rosetta; prefer avoiding those paths when possible.

### 6. Version Override Contract
- Any create/enable path that launches Docker/Podman containers, KinD clusters, Helm installs, or Multipass VMs must expose explicit flags for runtime versions/images.
- Keep sensible defaults for each flag, but never hardcode an image/channel/version without a user override path.
- For KinD/Helm, expose node image and chart version controls (example pattern: `--kind-node-image`, `--vso-chart-version`).
- For helper sidecars/proxies/support services (for example nginx/minio/openldap UI containers), expose image tag flags alongside primary product flags.

### 7. Engine Capacity Advisory
- Heavy HAL stacks should consult current engine capacity before large deploys, regardless of whether the engine is Docker or Podman.
- Prefer live engine data plus container stats for warnings, not guesses based only on static defaults.
- High-cost create paths should emit compact preflight notes when headroom is tight.
- Interactive confirmation prompts should only trigger when estimated post-create usage exceeds engine limits (CPU > 100% or RAM > machine RAM).
- `hal status` should surface current engine capacity and live usage so users can judge headroom before starting another stack.
- `hal capacity` defaults to the current view.
- `hal capacity --active` (or `--deployed`) shows active heavy deployment composition with per-stack footprint details.
- `hal capacity --pending` shows pending heavy deployment impact estimates.
- Capacity scenario labels should remain infra-centric where appropriate (for example shared GitLab runner and KinD/VSO flows), not exclusively product-centric.
- Memory pressure calculations should exclude cache/buffers (use pressure memory, not allocated/free-cache-inflated baselines).
- Podman on macOS can expose richer machine-runtime telemetry than Docker; use it when available, but keep the command functional for Docker too.

## Product Notes

- AAP lifecycle and Vault OIDC/SSH integration is managed via `hal vault aap enable|update|disable` (status is the default when no subcommand is given).
    - Default image is `ubi9-aap` and runs as container `hal-aap` on `hal-net`.
    - HTTPS is published locally on host port `443` by default (`https://aap.localhost`).
    - Use `--host-port` on `hal vault aap enable` if port 443 is already in use.
- Boundary target setup has version-sensitive API behavior around auth methods, grant strings, target host-source actions, and brokered credential source attachment.
- HAL MCP command namespace (`hal mcp`) supports two transports:
    - **stdio** (default, local/dev): `hal mcp serve` — spawned directly by HAL Plus. Default advertised protocol `2024-11-05`.
    - **streamable-HTTP** (container): `hal mcp serve --transport streamable-http --http-host 0.0.0.0 --http-port 8080 --http-path /mcp`. Default advertised protocol `2025-03-26`.
    - **Protocol version negotiation**: the `initialize` handler now honors the client's requested `protocolVersion`. Supported revisions (newest first): `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`. If the client requests a supported version it is echoed back; an unknown request returns the latest supported (`2025-11-25`); no request falls back to the per-transport default above. HAL Plus sends `2024-11-05` (stdio) / `2025-03-26` (http) and therefore keeps getting the same negotiated version — the pairing is unchanged.
    - **Streamable-HTTP request hardening**: the POST handler validates the `Origin` header (browser DNS-rebinding protection) — absent Origin (non-browser clients like HAL Plus) is allowed, loopback and `*.localhost` are allowed, anything else is `403`; extra origins can be allowlisted via `HAL_MCP_ALLOWED_ORIGINS` (comma list). A present-but-unsupported `MCP-Protocol-Version` header returns `400`; an absent header is tolerated for backwards compatibility. stdio still uses LSP-style `Content-Length` framing matched by the bundled HAL Plus client (not standard newline-delimited MCP stdio — a coordinated cross-repo change if ever migrated).
    - `hal mcp create --http` provisions the `ghcr.io/hashimiche/hal-mcp:latest` image for the streamable-http transport. It **uses a locally present image if one exists** (e.g. one built with `podman build -t ghcr.io/hashimiche/hal-mcp:latest -f Dockerfile.mcp .`) and only pulls from GHCR when the image is absent; pass `--pull` to force a registry refresh. No source tree or Go toolchain required on the user machine when pulling.
    - The image is published automatically by the release workflow (`Dockerfile.mcp`) on every version tag as `ghcr.io/hashimiche/hal-mcp:latest` and `ghcr.io/hashimiche/hal-mcp:<version>`. It runs as a non-root user (`hal`, uid 10001).
    - `--http-tag` flag overrides the pulled image tag (e.g. to pin a specific version).
    - `hal mcp create|serve|status|delete` remains the primary operator surface.
    - MCP tool surface is read-only and leverages existing HAL command paths (`status`, `capacity`, `<product> status`) instead of reimplementing product logic.
    - Product status tools (for example `get_tfe_status`) should keep product-specific `recommended_commands` first (`hal terraform status`) so AI clients can answer quick health prompts without falling back to generic checks like `hal capacity`.
    - `get_tfe_vcs_workflow_status` is a structured, read-only scenario tool for the Terraform VCS-driven workflow: it overlays live booleans (TFE runtime, `hal-gitlab` container, `~/.hal/tfe-app-api-token` presence) onto the canonical primary-target defaults (TFE org `hal` / project `Dave` / workspace `tfe-agent-demo`, GitLab `root/tfe-agent-demo` on `main`) and returns `data.{target,gitlab{web_url,...},tfe{workspace_url,runs_url,...},lab_credentials{gitlab,tfe_admin},ready}`. `lab_credentials` are non-secret demo values intentionally surfaced (lab-scoped, redaction-exempt). v1 covers the primary target only; twin degrades gracefully. The canonical endpoints/credentials are static hal defaults, so they are **always populated in `data`, including the runtime-unavailable error envelope** (only the `running`/`ready` booleans go false) — this lets HAL Plus render the deterministic Access/Observe sections even when the lab is down. The `tfe_admin` username is `haladmin` (the init-only `admin` user is reconciled to `haladmin` everywhere, including `hal creds status`).
    - `get_vault_pki_status` is a read-only status tool that runs `hal vault pki` (no flags = status mode) and returns the TEXT execution output covering the Root/Intermediate CA engines (`pki-root` + `pki-int`), the `hal-role` issuing role, the optional SoftHSM2 PKCS#11 managed key (`--hsm`: `sys/managed-keys/pkcs11/hal-kms-root`), cert-manager (`--k8s`: ClusterIssuer `vault-pki-issuer` + Certificate `hal-web-pki-cert` on the nginx pod at `https://pki.localhost:8089`) and ACME/Caddy (`--acme`: role `acme-demo`, 5m TTL auto-renewed at ~1/3 lifetime via Caddy at `https://acme.localhost:8090`). `recommended_commands` lead with `hal vault pki`, then the `enable`/`--hsm`/`--acme`/`--k8s` variants. Private keys never leave Vault (software or HSM token).
    - `get_active_credentials` is a structured, read-only tool that wraps `hal creds status` (via `creds.CollectActiveCredentials()`): it returns `data.{any_active,services[]}` where each service carries `{service,label,url,entries[{name,username,secret,note}],commands[]}` for currently running lab services (Vault + OIDC/LDAP/UserPass/Database, Boundary + SSH/MariaDB targets, TFE). When nothing is deployed it returns a `not_deployed` error envelope with `any_active:false`. Credentials live in the free-form `data` map (not the typed redaction-guarded `resp.Credentials` field), consistent with `lab_credentials` above. The live TFE API token is **deliberately NOT surfaced** here (the TFE entry carries a `note` pointing to `hal creds status`); only non-secret demo usernames/passwords are returned.
    - `get_capabilities`, `hal_policy_profile`, and `validate_command` are structured, read-only contract tools that require no engine access (so they stay green even in the socket-less `hal-mcp` container). `get_capabilities` enumerates the live surface from the skill index — `data.{contract_version,policy_version,tools[],actions[],commands[],deprecated_commands[],skills{skills_count,names[]}}`. `hal_policy_profile` (optional `profile`, default `strict`) returns the grounding policy HAL Plus prefetches: `data.{profile,answer_policy,tool_policy{required_prefetch_tools,on_uncertain_then_call,fallback},recommended_bootstrap,source}`. `validate_command` (`command` or `proposed_command`) wraps `validateCommand()`; valid input returns the normalized command, invalid input returns a `command_not_found` error envelope with suggestions. These four tools (`hal_status_baseline`, `get_capabilities`, `hal_policy_profile`, `validate_command`) are the prefetch contract HAL Plus relies on for its MCP health gate.
    - **Scenario/product status tools added for recent hal features** (all read-only, each wraps the matching `hal <product> <feature>` status path and returns a contract envelope): `get_boundary_ssh_status` (Multipass Ubuntu SSH target), `get_tfe_agent_status` (custom TFE agent pool), `get_tfe_twin_status` (second local TFE instance), `get_tfe_saml_status` (Authentik SAML SSO for TFE), `get_vault_userpass_status`, `get_vault_os_status` (Linux user-management secret engine via Ubuntu VM), `get_plus_status` (HAL Plus runtime: `hal-plus`/`hal-mcp`/`hal-qdrant`), and `get_version` (CLI version string). `get_product_obs_status` takes a required `product` enum (`vault|consul|nomad|boundary|terraform`) and reports that product's `hal <product> obs` Grafana/Prometheus/Loki integration — distinct from the standalone `hal obs` stack; obs uses CRUD (`create/update/delete/status`), not `enable/disable`.
    - `validate_command`'s allowlist tracks the live command surface: OIDC/SAML now use **Authentik** (`hal-authentik-server`/`hal-authentik-worker`), not the retired Keycloak; `hal terraform cli` is retired (rejected) while `hal terraform api-workflow|vcs-workflow|agent|twin|saml|obs` and their aliases (`api`, `vcs`/`workspace`/`ws`, `bis`/`dup`) are accepted; per-product `obs` and Vault `pki|userpass|os` are accepted.
    - The `hal-mcp` container does **not** mount the host container engine socket and does not run as root. Tool calls that require engine access (for example `hal_status_baseline`) will return an engine-unavailable error in rootless podman deployments — this is expected; HAL Plus handles it gracefully.
    - AI clients must treat this engine-unavailable baseline as **runtime unknown**, not as product up/down evidence. For quick status prompts, respond with `Unknown` and recommend the product-specific status command (for example `hal vault status`).
    - There is no SSH-based MCP transport pattern. Do not introduce or suggest SSH tunnelling for MCP.
- HAL Plus stack lifecycle is managed via `hal plus create|status|delete`:
    - `hal plus create` runs preflight checks (Ollama reachability, model availability, local MCP image presence), ensures `hal-net` exists, then starts `hal-mcp`, `hal-qdrant`, and `hal-plus` containers on `hal-net`.
    - `hal plus create --image <tag>` uses a local image directly if it exists (no forced pull); pulls from registry only when image is absent.
    - **Retrieval backend (`--rag`, default `qdrant`):** with `--rag qdrant` (default), create also preflights an embedding model (`--embed-model`, default `nomic-embed-text`, pulled on the host if missing), pulls/starts the pre-seeded `hal-qdrant` container (`ghcr.io/hashimiche/hal-plus-qdrant:latest`, override with `--qdrant-image`/`--qdrant-tag`), and injects `HAL_RAG_BACKEND=qdrant`, `HAL_QDRANT_URL=http://hal-qdrant:6333`, `HAL_DOC_SEARCH_EMBED_MODEL` into the `hal-plus` container. `--rag local` skips Qdrant entirely and uses the in-process (MiniSearch + Ollama rerank) backend. The pre-seeded image bakes the full vector corpus into `/qdrant/storage` (Qdrant v1.13.6 declares no VOLUME), so no crawl/embed of the corpus is needed at runtime — only the query is embedded via host Ollama. **The `hal-plus-qdrant` image is built/published by CI in its own dedicated repo (monthly cron + on-demand), independently of the hal binary release; it is NOT built locally or pushed from a laptop.** Tags: `:latest` + dated `:YYYY.MM.DD`.
    - `hal plus delete` tears down all three containers (`hal-plus`, `hal-mcp`, `hal-qdrant`).
    - `hal plus status` reports image presence, container state, and endpoint health for all three containers.
    - Ollama must run on the **host**. HAL Plus contacts it from inside the container via `host.containers.internal:11434` (podman) or `host.docker.internal:11434` (docker). `OLLAMA_BASE_URL` env var overrides the resolved URL.
    - No socket mounts, no `--user` overrides, no `DOCKER_HOST` injection into `hal-mcp`. Podman stays rootless.
- Terraform Enterprise local deployment depends on a mocked PostgreSQL, Redis, and MinIO stack and uses local TLS material under `~/.hal/tfe-certs`.
    - Rootless Podman path uses `https://tfe.localhost:8443` through `hal-tfe-proxy`.
    - TFE admin HTTPS is exposed through the same proxy at `https://tfe.localhost:8444`.
    - Twin TFE lifecycle is target-based on product CRUD commands (for example `hal terraform create --target twin`) instead of a dedicated `hal terraform twin` subcommand.
    - Terraform helper subcommands are lifecycle-only: `hal terraform api-workflow`, `hal terraform vcs-workflow`, and `hal terraform agent` accept `status|enable|disable|update` (no `create|delete` aliases).
    - `hal terraform api-workflow` target scope is `primary|twin` only; do not suggest `--target both` for this helper.
    - Custom local agent-pool flow uses `hal terraform agent enable` and should report running state via `hal terraform agent` before directing users to select Agent execution mode in TFE UI.
    - Task worker agent-run config must keep `/tmp/terraform` writable (not read-only) so remote plans can download Terraform binaries. The read-only mount is TFE's shared disk cache (`TFE_DISK_CACHE_VOLUME_NAME`/`TFE_DISK_CACHE_PATH`), which is **required** for the Docker run pipeline and cannot be removed. TFE renders the task-worker run config (`/run/terraform-enterprise/task-worker/config.hcl`) from the on-disk template `/etc/task-worker/config.hcl.tmpl` (which hardcodes `readonly = "true"`) **within ~40ms of container start** — far too early for any post-start `exec` patch, and this image has **no supervisord** to restart the task-worker (PID 1 is the `terraform-enterprise` process manager; `supervisorctl` has no socket and killing the task-worker does not respawn it). So the only reliable fix is a **bind mount present at container creation**: both `create.go` and `twin.go` call the shared helper `writableTaskWorkerTemplatePath(engine, image, hostDir)` (in `foundation.go`), which extracts the template from the **exact image tag** (`<engine> run --rm --entrypoint cat <image> /etc/task-worker/config.hcl.tmpl`, so no version drift), flips `readonly` to `false`, writes it to the host cert dir, and returns a path bind-mounted `-v <host>:/etc/task-worker/config.hcl.tmpl:ro`. TFE then renders the run config `readonly=false` from first boot. (History: earlier attempts patched the generated `/run` config after readiness and/or `supervisorctl restart tfe:task-worker` — both failed; the `/run` copy is rendered before any exec and there is no supervisord.)
    - TFE API responses can emit archivist object links without `:8443`; proxy response rewriting keeps UI/raw plan/apply log links host-reachable.
    - **VCS commit-status link port (ACCEPTED LIMITATION, verified):** the run link TFE POSTs to GitLab commit statuses comes out as `https://tfe.localhost/...` (no `:8443`) and is not host-reachable. It is built from the **primary** `TFE_HOSTNAME`, which is intentionally portless so the rest of the deployment works behind `hal-tfe-proxy`. This is **not** fixable via a secondary hostname: an experiment set `TFE_HOSTNAME_SECONDARY=tfe.localhost:8443` + `TFE_VCS_HOSTNAME_CHOICE=secondary` — TFE booted fine (it accepts a port in that var) but the commit-status link **stayed portless**, because `TFE_VCS_HOSTNAME_CHOICE` only governs VCS *workload-identity federation*, not the human-facing run link. The proxy can't rewrite it either (outbound TFE→GitLab, not served through the proxy). Only moving the **primary** `TFE_HOSTNAME` to include `:8443` would change it, which has too broad a blast radius. Left as-is; the dead `TFE_VCS_HOSTNAME` no-op (not a real setting) was removed from create.go/twin.go. Do not re-attempt the secondary-hostname route.
    - `hal terraform vcs-workflow enable` should describe validation in terms of pushing a new commit to `main`; tag creation alone is not a reliable first-run trigger when the tagged SHA was already ingested from branch pushes.
    - `hal terraform vcs-workflow` exposes GitLab tuning flags (visible in `--help`, same names as `hal vault jwt`): `--gitlab-image` (default `gitlab/gitlab-ce`) + `--gitlab-tag` (default `18.10.1-ce.0`) form the full CE image ref, and `--gitlab-port` (default `8080`) sets the shared GitLab host/container port (override when host `8080` is taken). These only apply when HAL boots a fresh `hal-gitlab`; an already-running shared GitLab is reused as-is. GitLab listens internally on the same `--gitlab-port`, so the TFE→GitLab OAuth `http-url`/`api-url` and the host CLI/browser URLs all track that port. (Other advanced flags — `--gitlab-root-password`, `--tfe-*`, `--project-*` — stay hidden.)
    - **Shared GitLab bring-up is centralized**: `hal-gitlab` is a singleton shared by `hal vault jwt` and `hal terraform vcs-workflow`. Both call `integrations.EnsureSharedGitLab(engine, image, rootPassword, requestedPort, waitSeconds)` — the single provisioning path. When GitLab is already running (booted by the other product, possibly on a custom port), `requestedPort` is ignored and the live port is detected via `integrations.DetectGitLabPort` and returned in the `GitLabHandle`. Each caller then adopts `handle.Port` for every downstream URL (host `127.0.0.1:<port>`, alias `gitlab.localhost:<port>`, container `hal-gitlab:<port>`), so a lab spun up by TF on a non-default port is consumed correctly by `vault jwt` (and vice-versa) with no port drift. Both products expose the **same** GitLab flag names — `--gitlab-tag`, `--gitlab-image`, `--gitlab-port` (vault jwt adds `--gitlab-runner-image`/`--gitlab-runner-tag`) — since they configure the same shared service.
    - **Shared-service teardown is consumer-aware** (symmetric with bring-up, for both GitLab and Authentik): the shared `hal-gitlab` (registry key `gitlab`) and the Authentik stack (`AuthentikSharedServiceKey`) are only removed once the last consumer deregisters. `hal vault jwt disable`, `hal vault delete`, and `hal terraform vcs-workflow disable` each call `global.RemoveSharedServiceConsumer` and preserve shared GitLab while any consumer remains **or** a TFE runtime (`hal-tfe`/`hal-tfe-bis`) is still running (see `teardownSharedGitLab` in `cmd/vault/jwt.go`); the vault-jwt-only `hal-gitlab-runner` is always removed. Likewise `hal vault oidc disable`, `hal vault delete`, and `hal tf saml disable` keep the Authentik stack up while another product still uses it. Consequently `hal vault delete` no longer force-removes `hal-gitlab`/Authentik out from under a running TF lab — both are intentionally **excluded** from the unconditional `vaultEcosystem` nuke list in `cmd/vault/delete.go`. (The OIDC status probes in `hal status`/`hal vault status`/`status_snapshot.go` now inspect `hal-authentik-server`, never the retired `hal-keycloak`.)
    - The top-level `hal terraform` command accepts the aliases `tf` and `tfe` (both normalized to `terraform` in MCP `validate_command` and display normalization).
    - **GitLab image preflight**: before a fresh boot, `EnsureGitLabCE` runs `integrations.EnsureImageAvailable(engine, image)` which (1) rejects malformed refs — notably a bare version passed as an image like `18.10.1-ce.0` (the classic "pulled as `18.10.1-ce.0:latest` → pull access denied" failure) with a hint to set `--gitlab-image`/`--gitlab-tag`, and (2) ensures the image is present locally, streaming a `docker pull` (with progress, since GitLab CE is multi-GB) and turning registry/tag failures into a clear message instead of a raw engine error mid-boot.
- `hal health` is a CRUD product that manages the `hal-health` sidecar container:
    - `hal health create` / `hal health update` / `hal health delete` are the operator surface.
    - `hal health update` is the manual escape hatch: refreshes the snapshot for the currently running ecosystem (e.g. after deploying a product extension outside the normal lifecycle).
    - `hal health _serve` is a hidden internal command run inside the `hal-health` container — do not surface it to users.
    - The `hal-health` container reuses `hashimiche/hal-mcp:latest` (same image as `hal-mcp`) with `--entrypoint /usr/local/bin/hal` and `health _serve` as args.
    - It reads a frozen `HAL_HEALTH_DATA` JSON env var at startup and serves it at `http://hal-health:9001/api/status` on `hal-net`.
    - The snapshot is built on the **host** (which has engine socket access) by `global.RefreshHalHealth(engine)`, injected as an env var, then the container is recreated. The container itself never touches the engine.
- `global.RefreshHalHealth(engine)` is called after every product lifecycle event that changes ecosystem state: all product `create`/`delete` commands, and all vault/boundary extension enable/disable commands (`vault k8s`, `vault oidc`, `vault jwt`, `vault aap`, `vault ldap`, `vault database`, `boundary mariadb`, `boundary ssh`).
    - `RefreshHalHealth` is a no-op if `hal-net` does not exist or the `hashimiche/hal-mcp:latest` image is not present — safe to call unconditionally.
    - HAL Plus fetches `http://hal-health:9001/api/status` as its primary product state source (via `fetchHalStatusProducts()` in `server/index.mjs`), with `fallbackProductsFromEndpoints()` as a fallback for local dev without containers.
    - The snapshot shape: `{ timestamp, engine, products: [{ product, state, health, reason, endpoint, containers, features: [{ feature, state, health, reason }] }] }`.
- `hal vault create` has two deployment modes via `--mode` (default `dev`):
    - **`dev`** (unchanged): `vault server -dev`, in-memory, auto-unsealed, plaintext HTTP at `http://vault.localhost:8200`, well-known `root` token. `--edition ent` uses the Enterprise image but stays in dev mode.
    - **`prod`**: single-node **production Vault Enterprise** — real `vault server -config` with **integrated Raft** storage on the persistent `hal-vault-data` volume, **TLS** at `https://vault.localhost:8200` (self-signed cert forged under `~/.hal/vault-prod/certs/`, mirrors the TFE `ensureCerts` pattern), and automatic `operator init` (default `--key-shares 1 --key-threshold 1`, overridable) + `unseal`. Implies `--edition ent`; `--edition ce --mode prod` is rejected. Requires `VAULT_LICENSE`/`VAULT_LICENSE_PATH` (reuses the existing license gate). Prod-only flags: `--key-shares`, `--key-threshold`, `--node-id`.
    - **Credential standard**: the raw `vault operator init -format=json` output is cached to `~/.hal/vault-prod/init.json` (mode `0600`) via `internal/global` helpers (`CacheVaultInit`/`LoadCachedVaultInit`/`RemoveCachedVaultInit`/`VaultInitCachePath`/`VaultProdCertPath`), mirroring `tfe_token_cache.go`. The unseal key + root token are surfaced by the create summary, `hal vault status`, and `hal creds status` (with `VAULT_CACERT`). `hal vault delete` removes `~/.hal/vault-prod/`.
    - **Prod detection**: host-side code treats prod as active when `~/.hal/vault-prod/certs/cert.pem` exists (`vaultProdActive()` in `cmd/vault/helper.go`). `GetHealthyClient` then uses the HTTPS address + forged CA + cached root token, so all feature commands routing through it (audit, ldap, userpass, os, aap, jwt, oidc) connect over TLS with no manual `VAULT_ADDR`.
    - **Known scope limit (deferred)**: features that write `http://vault.localhost:8200` URLs *into* Vault — OIDC callback/redirect URIs (`oidc.go`), PKI AIA/CRL/ACME directory URLs (`pki.go`), and the in-container `vault plugin register` (`os.go`) — are still http-oriented; validate those flows against **dev mode** until a follow-up makes them scheme-aware.
